# Jev 판단 보조 — 선택 기능

> 우리 설계에는 **LLM 이 판단하고 그 판단을 그냥 믿는 지점**이 있다.
> Jev 는 그 판단을 텍스트가 아니라 **타입 있는 값 + 확률**로 받게 해준다.
>
> **없어도 제품은 그대로 돌아간다.** 있으면 판정이 더 단단해진다.

---

## 어디에 쓰나

| 판정 | 지금 | Jev |
|---|---|---|
| **모호함** (DIALOGUE §5.1) | 프롬프트가 "해석 갈래 × 격차"를 판단 | `Score` 두 개를 곱해 **강도 0~4** 산출 |
| **타당성 3색** (PROTOCOL §8.2) | 프롬프트가 🟢🟡🔴 판단 | `Choice` + 확신도 |
| **변경 분류** (CHANGE.md §2) | 프롬프트가 추가/변경/버그 판단 | `Choice` + 확신도 |

모호함이 가장 값어치 있다. DIALOGUE §5.1 에 **"자기 확신도는 잘 보정되지 않고 대체로 과신한다"**
고 써놓고서도 결국 그 판단에 맡겼다. 확률이 나오면 임계를 실제로 걸 수 있다.

**게이트는 쓰지 않는다.** AC 존재·근거 형식은 이미 기계가 정확히 검사한다.
확률이 필요한 곳은 판단이지 검사가 아니다.

## 켜는 법

```bash
export TYPESAFE_API_KEY=...        # console.typesafe.ai/keys
devoffice judge ambiguity "잔액 화면 좀 바꿔주세요"
```

키가 없으면 "꺼져 있음"이라고만 말하고 **그대로 진행한다.**

```bash
devoffice judge feasibility "서울 부동산 호가 리스트를 보여주고 싶어요"
devoffice judge change "종목 찾기 빼고 전략 선택으로만 해주세요"
devoffice judge ambiguity "..." --json        # 원본 응답
```

## 왜 사용자에게 선택지로 내밀지 않나

**비개발자에게 묻는 순간 원칙 세 개를 깬다.**

| 원칙 | 왜 깨지나 |
|---|---|
| P5 결정은 우리가 | 기술 선택을 사용자에게 떠넘기는 것이다 |
| S3 계정은 최소로 | 네 번째 계정 + API 키. 여기가 이탈 1순위다 |
| 의존성 0 | 가격이 **공개돼 있지 않은** 외부 서비스가 필수가 된다 |

그리고 사용자는 **판단 정확도의 차이를 평가할 수 없다.** 물어봐도 답할 수 없는 질문이다.

→ **환경변수로만 켠다.** 있으면 쓰고, 없으면 지금처럼 한다. 사용자는 존재를 몰라도 된다.
`expo check`(오프라인이면 추측 안 함)·Artifact(없으면 ASCII) 와 같은 폴백 패턴이다.

## 실패해도 멈추지 않는다

| 상황 | 동작 |
|---|---|
| 키 없음 | 프롬프트 판단으로 진행 |
| 네트워크·타임아웃(20초) | 프롬프트 판단으로 진행 |
| 401 / 429 / 529 | 프롬프트 판단으로 진행 |

**외부 서비스가 죽어서 제품이 멈추면 안 된다.** `evaluate()` 는 던지지 않고
`{ ok:false, reason }` 을 돌려준다.

## 도입 절차 — 이 순서로만 간다

```
1. 키 발급            (신청 중)
2. devoffice judge testset      기대값과 나란히 비교
3. 효과 판정           아래 기준으로
4. 효과 있으면 → 스킬에 연결 + 사용자 옵트인 경로
5. 효과 없으면 → 붙이지 않는다. 지시문만 다듬거나 폐기
```

### 2단계 — 기대값을 미리 정해뒀다

```bash
export TYPESAFE_API_KEY=...
devoffice judge testset                 # 전부
devoffice judge testset --only ambiguity
```

17개 문장에 **기대 판정을 미리 적어뒀다.** 우리 설계 논의에서 실제로 나온 문장들이다.

| 문장 | 기대 |
|---|---|
| "버튼을 파랗게 해주세요" | 강도 0~2 |
| "글 목록 정렬해줘" | 강도 2~4 |
| "회원 등급 만들어줘" | 강도 3~4 (권한이면 되돌리기 어렵다) |
| "서울 부동산 호가 리스트" | 🔴 red |
| "댓글에 사진도" | add |
| "댓글이 안 지워져요" | bug |

> **키를 받은 뒤 "좋아 보인다"로 판단하면 그건 측정이 아니라 인상이다.**
> 그래서 정답을 먼저 적어뒀다.

### 3단계 — 판정 기준

| 결과 | 결론 |
|---|---|
| 거의 다 맞음 | **붙일 가치가 있다** |
| 절반쯤 | `criteria` 지시문을 다듬어 다시 |
| 많이 틀림 | **붙이지 않는다.** 프롬프트가 낫다 |

그리고 숫자 말고 **한 가지를 더 본다:**
같은 문장을 프롬프트로도 판단시켜서 **둘이 다를 때 어느 쪽이 맞는지** 본다.
같은 답을 내면 붙일 이유가 없다.

---

## 4단계 — 사용자에게 어떻게 물을까

효과가 확인되면 옵트인 경로를 만든다. **다만 문구를 조심해야 한다.**

### 이렇게 묻지 마라

| ❌ | 왜 |
|---|---|
| "에이전트 간 통신 방식을 향상시킬까요?" | **기술 용어.** 비개발자에게 무의미하다 |
| "판단 정확도를 높일까요?" | 정확도 차이를 **사용자가 평가할 수 없다** |
| "Jev 를 연결할까요?" | 제품 이름을 사용자가 알 필요 없다 |

### 이렇게 묻는다 — 사용자가 겪는 일로

```
제가 말씀을 잘못 이해해서 다시 여쭤보는 일이 몇 번 있었죠.
그걸 줄이는 방법이 있어요.

 ① 지금처럼 진행          추가로 필요한 건 없어요
 ② 조금 더 정확하게        가입 하나가 더 필요해요 (○분, 무료 한도 있음)

 ※ ①로 하셔도 다 만들 수 있어요. ②는 되묻는 횟수가 줄어드는 정도예요.
```

**세 가지를 지킨다:**
1. **사용자가 실제로 겪은 일**로 말한다 — "다시 여쭤보는 일이 줄어요"
2. **①로도 충분함을 명시한다.** 없으면 못 만드는 것처럼 들리면 안 된다
3. **비용을 정직하게** — 가입 개수와 무료 한도

그리고 **묻는 시점**이 중요하다. 처음(S3 계정 만들 때)에 묻지 않는다 —
그때는 사용자가 왜 필요한지 모른다. **되묻기가 실제로 몇 번 일어난 뒤**에 묻는다.

## 확인해야 할 것 (아직 모름)

- **가격.** 문서에 pricing·billing·free tier 페이지가 아예 없다. 콘솔 로그인이 필요하다
- **한국어 성능.** 우리 판정 문구는 전부 한국어다
- **지연.** 매 발화마다 부르면 대화가 느려진다. 실제로 몇 ms 인지 재봐야 한다
- **정확도가 프롬프트보다 나은가.** 이게 증명되지 않으면 붙일 이유가 없다

→ `devoffice judge` 로 같은 문장을 프롬프트 판단과 나란히 비교해보고 판단한다.
**나아지는 게 확인되기 전에는 스킬에 연결하지 않는다.**
