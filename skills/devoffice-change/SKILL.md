# 기능 바꾸기

**사용자는 "수정"과 "추가"를 구분하지 않는다.** 그리고 지금 어느 상태인지도 모른다.
같은 말이 10초짜리 일일 수도, 되돌릴 수 없는 1시간짜리 일일 수도 있다.

**우리가 판정하고 알려준다. 추측하지 않는다.**

---

## ⓪ 변경 요청은 대부분 모호하다 — 세 가지를 먼저 확정한다

실제로 이런 말이 온다.

> "계획했던 종목 찾기 기능을 추가하지 말고 전략을 선택하는 형태로만 변경해서 진행해주세요"

한 문장에 **모호함이 세 겹**이다.

| 겹 | 무엇이 모호한가 | 이 문장에서 |
|---|---|---|
| **대상** | 어느 기능을 말하는가 | "종목 찾기"가 F-001 맞나? "전략 선택"은 이미 있는 F-003인가? |
| **동작** | 빼는가 · 미루는가 · 바꾸는가 | "추가하지 말고" = 삭제? 보류? |
| **목적지** | 바꾸고 나면 어떤 모습인가 | F-002·F-004는 어떻게 되나? |

**이 셋을 확정하기 전에 아무것도 고치지 마라.** 잘못 고치면 되돌리는 게 더 비싸다.

---

### 먼저 정확한 현재 목록을 본다

```bash
devoffice backlog list
```

**기억에 의존해서 목록을 말하지 마라.** 12개 중 어느 것인지 정확해야 한다.

### 대상을 짚어서 확인한다

이름이 정확히 안 맞을 수 있고, **말한 것이 이미 목록에 있을 수도 있다.**

```
말씀하신 걸 이렇게 짚었어요. 맞나요?

  빼려는 것   1번 "종목을 찾아서 담을 수 있어요"
  남기려는 것 3번 "준비된 전략 중에 고를 수 있어요"   ← 이미 목록에 있어요

👉 맞으면 "네", 다른 걸 말씀하신 거면 번호로 알려주세요
```

> **"이미 목록에 있어요"를 반드시 짚는다.** 새로 만들려던 게 이미 있으면
> 만들 게 아니라 **순서를 앞으로 당기는 일**이다.

### "빼기"는 네 가지다 — 반드시 나눠서 묻는다

사용자는 구분해서 말하지 않지만 **되돌리기 비용이 완전히 다르다.**

```
"종목 찾아서 담기"를 어떻게 할까요?

 ① 나중으로 미루기      정한 내용은 남고 순서만 뒤로 가요      ← 추천
 ② 목록에서 아예 빼기    정한 내용도 같이 지워져요
 ③ 다른 걸로 바꾸기      어떻게 바꿀지 말씀해주세요
 ④ 그대로 두기

 ※ ①은 언제든 되돌릴 수 있어요. ②는 다시 정하셔야 해요.
```

**①을 기본 추천으로 둔다.** 되돌릴 수 있는 쪽이 항상 안전하다.
F-001처럼 **명세와 그림까지 만들어둔 기능이면 더더욱** — 지우면 그 작업이 사라진다.

## ⓪-b 파급을 제품 언어로 보여준다

```bash
devoffice feature impact <ID>
```

**단, 출력을 그대로 옮기지 마라.** "F-004가 의존해요"는 비개발자에게 아무 의미가 없다.
**"이래서 안 된다"로 바꿔 말한다.**

| ❌ 기술 언어 | ⭕ 제품 언어 |
|---|---|
| "F-004가 F-001에 의존합니다" | "종목을 못 담으면 **전략을 붙일 대상이 없어져요**" |
| "F-002가 영향받습니다" | "담은 게 없으니 **가격 볼 것도 없어져요**" |

`impact` 가 **"무엇이 같이 바뀌는지 모르는 상태"**라고 하면 —
연결이 기록돼 있지 않다는 뜻이다. **"영향 없음"이라고 말하지 마라.**
목록을 직접 읽고 판단한 뒤, 그 판단을 사용자에게 확인받는다.

---

## ⓪-c 목적지를 보여주고 확인받는다 ★ 가장 중요

개별 기능을 하나씩 물으면 사용자는 답을 모른다. **자기도 그 수준으로 생각하지 않았다.**

> **바뀐 후의 목록을 보여주는 것이 답이다.**
> 비개발자는 추상적 변경을 판단하지 못하지만 **눈앞의 목록에는 "이거 아니에요"를 정확히 말한다.**

```
말씀대로 바꾸면 목록이 이렇게 돼요.

  지금                            바꾸면
  ──────────────────────────      ──────────────────────────
  1. 종목을 찾아서 담기            1. 준비된 전략 중에 고르기
  2. 담은 종목과 가격 보기         2. 종목에 전략을 붙여 감시 켜기
  3. 준비된 전략 중에 고르기        3. 매매 엔진을 서버에 올리기
  4. 종목에 전략을 붙여 감시 켜기   ...
                                  (맨 뒤) 종목을 찾아서 담기 — 미뤄둠
                                  (맨 뒤) 담은 종목과 가격 보기 — 미뤄둠

  ⚠️ 이렇게 하면 걸리는 게 있어요
     전략은 고를 수 있는데 **어느 종목에 적용할지 정할 방법이 없어져요.**
     2번(전략 붙이기)이 대상 없이 남습니다.

     ① 종목 담기는 남기고 순서만 뒤로            ← 추천
     ② 종목을 하나만 미리 정해두고 시작
     ③ 그래도 전략만 먼저 만들기

👉 어떻게 할까요?
```

**⚠️ 부분이 핵심이다.** 사용자는 "종목 찾기를 빼면 매매 대상이 없어진다"는 걸 모른다.
목록만 바꿔 보여주고 끝내면 **나중에 만들다가 막힌다.**

## ① 그다음 분류한다

```
명세대로 만들었는데 그대로 안 되나?
  YES → 버그다 (§5). 기능 수정이 아니다

기존 동작이 그대로 남는가?
  YES → 작으면(AC 1개 이하) 수정 / 크면 **새 기능으로 쪼갠다**
  NO  → 수정 (§3)
```

| 사용자 말 | 판정 |
|---|---|
| "댓글에 사진도" | **새 기능** — 기존 댓글은 그대로 동작 |
| "500자를 1000자로" | 수정 (작다) |
| "대댓글도 되게" | 수정 — 구조가 바뀐다 |
| "삭제 기능 빼주세요" | 수정 |
| "댓글이 안 지워져요" | **버그** |

### 추가는 새 기능으로 쪼갠다

**이미 확인받은 것을 다시 흔들지 않기 위해서다.**
수정으로 처리하면 검증 완료였던 기능이 미검증으로 돌아가 잠금에 걸린다.

```
그건 지금 있는 댓글은 그대로 두고 사진 기능을 얹는 거예요.
목록에 새 항목으로 넣을게요 — 10개에서 11개가 돼요.

 ① 지금 만들기      ② 목록에만 넣고 나중에      ← 추천
```

## ② 상태와 영향을 확인한다 — 말하기 전에

```bash
devoffice feature impact <ID>
```

**이걸 먼저 실행한다.** 상태·되돌리기 난이도·예상 시간·영향받는 기능·데이터 위험을
계산해서 준다. 여기 없는 내용을 지어내지 마라.

---

## ③ 상태별로 다르게 대응한다

### 목록에만 있음 — 그냥 고친다

제목·순서·삭제는 바로 처리한다. **의존성만 확인한다.**

```
"전략 고르기"를 빼면 "전략 붙이기"도 못 만들어요.
 ① 둘 다 빼기   ② 그대로 두기   ③ "전략 붙이기"를 다르게 바꾸기
```

### 어떻게 만들지까지 정해짐 — 구체화를 다시

코드가 없으니 버릴 건 문서뿐이다.

- AC 하나 고치기 → `spec.md` 부분 수정 → `gate spec`
- **화면 구성이 바뀜** → `devoffice-spec` 으로 **처음부터 다시**
- 그림이 있으면 **같은 링크를 갱신**한다. 새로 만들면 어느 게 최신인지 헷갈린다

### 만들어짐 — 다시 열어서 고친다

```bash
devoffice feature reopen <ID> --reason "..."
```

**다시 미검증 상태가 된다.** 고친 뒤 사용자가 또 확인해야 한다.
"고쳐뒀어요"로 끝내면 안 고쳐진 채로 넘어간다.

수정도 만들 때와 같은 절차를 탄다 — 명세 → 계약 → 구현 → 검증.
다만 **바뀌는 부분만**.

---

## ④ 데이터가 있으면 반드시 묻는다

`impact` 가 "실제로 쓰이는 중"이라고 하면 **규칙이 달라진다.**

1. **백업 먼저.** 예외 없음
2. **기존 데이터를 어떻게 할지 사용자에게 묻는다** — 우리가 정할 수 없다
3. **되돌릴 수 없음을 명시**하고 확인받는다

```
지금까지 기록된 잔액이 500건 있어요.
새로 "실현손익" 항목이 생기는데, 그 500건에는 그 값이 없어요.

 ① 전부 0으로 채우기       간단해요. 다만 실제 값은 아니에요
 ② 비워두고 "-" 로 표시    정직해요. 화면에 빈칸이 보여요      ← 추천
 ③ 예전 것부터 다시 계산    정확하지만 오래 걸려요

 ⚠️ 이건 되돌릴 수 없어요. 고르시면 500건이 그대로 바뀝니다.
```

**②를 기본 추천으로 둔다. 데이터를 지어내지 않는 쪽이 항상 안전하다.**

### 항목을 빼는 건 특히 위험하다

지우면 그 데이터는 사라진다. **감추는 것을 먼저 제안한다.**

```
 ① 화면에서만 안 보이게 (데이터는 남아요)   ← 추천. 나중에 되돌릴 수 있어요
 ② 완전히 지우기 (되돌릴 수 없어요)
```

---

## ⑤ 버그는 기능 수정이 아니다

명세를 바꾸지 않는다. 새 기능으로 만들지 않는다. 백로그에 넣지 않는다. **바로 고친다.**

```
그건 제가 잘못 만든 거예요. 바로 고칠게요. 10분쯤이요.
새로 만드는 게 아니라서 목록은 그대로예요.
```

**"제가 잘못 만들었다"고 먼저 말한다.** 비개발자는 자기가 잘못한 줄 알고 위축된다.

고친 뒤 **그 상황을 검증 항목에 추가한다.** 같은 버그가 두 번 나면 안 된다.

---

## ⑥ 말리지 않는다. 더 싼 길을 먼저 보여준다

사용자 제품이다. 다만 **비용을 정직하게 말하고 대안을 함께 준다.**

| 상황 | 먼저 제안할 것 |
|---|---|
| 데이터 항목 삭제 | 화면에서만 감추기 |
| 큰 구조 변경 | 새 기능으로 옆에 만들고 나중에 갈아타기 |
| 여러 기능이 얽힘 | 하나씩 나눠서 |

**"40분 걸려요"를 안 말하면 나중에 신뢰를 잃는다.**

## 하지 말 것

- **대상을 확정하지 않고 고치기** — 12개 중 어느 건지 짚어서 확인받는다
- **"빼기"를 한 종류로 처리하기** — 미루기와 지우기는 되돌리기 비용이 완전히 다르다
- **바뀐 후 목록을 안 보여주기** — 말로 설명하면 사용자는 판단하지 못한다
- **파급을 기술 언어로 말하기** — "F-004가 의존해요"는 아무 의미가 없다
- **이미 목록에 있는 걸 새로 만들기** — 순서만 당기면 되는 경우가 많다
- 연결이 기록 안 됐는데 **"영향 없음"이라고 말하기** — 그건 "모른다"이다
- `impact` 를 안 돌리고 "금방 돼요"라고 말하기
- 영향받는 다른 기능을 안 알리기 — 나중에 그 화면이 깨져 있다
- 실 데이터가 있는데 기존 데이터 처리를 **우리가 정하기**
- 수정 후 확인을 안 받고 "고쳐뒀어요"로 끝내기
- 추가를 수정으로 처리해서 **확인 완료였던 기능을 미검증으로 되돌리기**
- 버그를 백로그에 새 기능으로 넣기
