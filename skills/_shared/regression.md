# 회귀 — 사용자가 한 번 확인한 것은 다시 깨지지 않는다

> 4중 게이트는 **이번 기능만** 본다.
> 21번째 기능을 만들다가 3번 기능이 깨져도 아무도 보지 않는다.
> 사용자는 자기가 안 건드린 화면을 다시 확인하지 않는다.
>
> **가능성이 아니라 예정된 사고다.**

---

## 1. 재료는 이미 있다 — `verify.md`

사용자가 직접 눌러서 **"됩니다"라고 말한 시나리오**다.
따로 테스트를 짤 필요가 없다. **그걸 그대로 자동화한다.**

```
① qa 가 verify.md 작성          "스위치를 누르면 '1개 켜짐'이 된다"
② 사용자가 확인                  ✅
③ qa 가 같은 시나리오를 테스트로   ← 여기가 회귀의 시작
④ 이후 모든 기능에서 전체 실행
⑤ 깨지면 "3번 기능이 깨졌어요"
```

**사용자는 테스트의 존재를 알 필요가 없다.** 확인하는 것도 이미 하던 일이다.

---

## 2. 무엇이 자동화되고 무엇이 안 되나 — 정직하게 나눈다

`verify.md` 의 모든 항목이 자동화되지는 않는다. **섞어두면 둘 다 못 쓴다.**

| 자동화된다 | 안 된다 |
|---|---|
| 화면이 그려지는가 | QR 찍어서 앱 열기 |
| 버튼을 누르면 상태가 바뀌는가 | 실기기에서 손가락으로 스크롤 |
| 빈 상태·에러 문구가 나오는가 | 실제 서버·증권사 응답 |
| 계산 결과가 맞는가 | 푸시 알림 |
| 저장했다가 다시 읽으면 남아 있는가 | 폰 화면에서의 실제 크기·느낌 |

**자동화 못 하는 것은 `regression.md` 에 수동 체크리스트로 남긴다.**
없애지 않는다 — 배포 전에 사람이 한 번 훑는다.

---

## 3. 스택별 도구

### mobile-expo

```bash
npx expo install -- --save-dev jest-expo jest @testing-library/react-native @types/jest
```

`package.json`:

```json
{
  "scripts": { "test": "jest" },
  "jest": { "preset": "jest-expo" }
}
```

**실기기·시뮬레이터가 필요 없다.** 컴포넌트를 메모리에서 그려보고 확인한다.

```tsx
// __tests__/F-003.strategies.test.tsx
import { render, fireEvent } from '@testing-library/react-native';
import App from '../App';

// verify.md 1번: 스위치를 누르면 "1개 켜짐" 으로 바뀐다
test('전략을 켜면 위쪽 개수가 늘어난다', () => {
  const { getByText, getAllByRole } = render(<App />);
  expect(getByText(/4개 중 0개 켜짐/)).toBeTruthy();

  fireEvent(getAllByRole('switch')[0], 'valueChange', true);
  expect(getByText(/4개 중 1개 켜짐/)).toBeTruthy();
});
```

**테스트 이름을 `verify.md` 항목 그대로 쓴다.** 깨졌을 때
사용자에게 뭐라고 말할지가 바로 나온다.

### web-next

```bash
npm i -D @playwright/test && npx playwright install chromium
```

브라우저를 실제로 띄워 클릭한다. Expo 보다 커버 범위가 넓다.

## 4. 파일 배치

```
__tests__/
  F-003.strategies.test.tsx     ← 기능 ID 를 파일명에 넣는다
.devoffice/features/F-003/
  regression.md                  ← 자동화 못 한 항목 (수동 체크리스트)
```

**기능 ID 를 파일명에 넣는 이유:** 깨졌을 때 어느 기능인지 즉시 안다.
`devoffice gate regression` 이 그걸 읽어 **"3번 기능이 깨졌어요"** 로 번역한다.

---

## 5. 깨졌을 때 — 신뢰를 얻는 순간이다

```
⚠️ 새 기능을 넣다가 예전에 확인하셨던 [전략 고르기]가 안 되게 됐어요.

   "전략을 켜면 위쪽 개수가 늘어난다" 가 안 돼요.
   고치고 다시 확인해드릴게요. 2분쯤이요.
```

**사용자가 신뢰를 잃을 순간이 오히려 신뢰를 얻는 순간이 된다.**
우리가 먼저 발견했고, 어느 기능인지 알고, 고칠 수 있다.

---

## 6. 언제 넣나

**기능이 5개를 넘기 전에.** 필요해졌을 때 만들면 이미 늦다 —
그때는 과거 기능의 시나리오가 자동화되어 있지 않아서, 처음부터 다시 짜야 한다.

첫 도입은 **한 번만** 하면 된다(도구 설치 + 설정). 그다음부터는
기능마다 테스트가 한두 개씩 쌓인다.

---

## 7. 하지 말 것

- **테스트를 위한 테스트 짜기.** `verify.md` 에 없는 걸 테스트하지 않는다
- 커버리지 숫자 쫓기 — 사용자가 확인한 것만 지키면 된다
- 자동화 못 하는 걸 억지로 자동화하기 (실기기·실제 결제·외부 API)
- **깨진 테스트를 지워서 통과시키기** — 그건 기능을 버리는 것이다
- 수동 체크리스트를 없애기 — 자동화 못 한 것도 확인은 해야 한다
