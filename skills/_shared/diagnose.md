# 막혔을 때 — 진단 규칙

> 구현 중 막히면 블로커를 남기고 멈춘다(house-rules 3번).
> **사용자 환경에서 막히는 건 다른 문제다.** 멈출 수 없고, 원인을 찾아야 한다.
> 이 문서는 그때의 규칙이다.

---

## 왜 이 문서가 있는가

실제로 일어난 일이다.

> 폰에서 앱이 안 열렸다. 네 번을 시도했다.
> ① "방화벽 문제일 거예요" → 아니었다
> ② "이 버튼을 누르세요" → 그 버튼은 없어진 지 오래였다
> ③ "카메라로 찍으세요" → 안 됐다
> ④ "Expo Go를 업데이트하세요" → **이미 최신이었다. 불가능한 걸 시켰다**
>
> 사용자가 "정확하게 원인을 파악하세요"라고 한 뒤에야 실제 로그를 봤다.
> **진짜 원인은 처음부터 명령 한 줄로 확인 가능했다.**

**추측한 이유는 게을러서가 아니라 "무엇을 확인해야 하는지 몰라서"다.**
모르면 그럴듯한 가설이 나오고, 가설은 진전처럼 보인다.

그래서 이 문서는 "추측하지 마라"라고 말하지 않는다. **어디를 봐야 하는지**를 말한다.

---

## 1. 확인 순서 — 싼 것부터

**절대 뒤집지 마라.** 위에서부터 내려간다.

| | 방법 | 비용 | 예 |
|---|---|---|---|
| **1** | 명령 한 줄로 확인 | 3초 | 버전, 프로세스, 포트, 파일 존재 |
| **2** | API·레지스트리 조회 | 5초 | 스토어에 올라온 버전, 패키지 최신판 |
| **3** | 우리가 만든 로그 읽기 | 10초 | 서버 로그에 상대가 남긴 정보 |
| **4** | 사용자에게 **보이는 것**을 묻기 | 1왕복 | "화면 캡처를 보여주세요" |
| **5** | 사용자에게 **해보라고** 하기 | 여러 왕복 | "다시 눌러보세요" |

> **4·5부터 시작하면 안 된다.** 위 사례는 5번부터 시작해서 1번을 마지막에 했다.
> 1~3은 사용자를 기다리게 하지 않는다. **먼저 다 해라.**

### 1단계에서 항상 보는 것

- **우리가 켠 것이 실제로 살아 있는가** — 백그라운드로 띄웠으면 응답하는지 확인
- **양쪽 버전이 맞는가** — 우리가 만든 것 ↔ 사용자 환경이 받아들이는 것
- **경로·파일이 실제로 있는가**

**첫 번째가 가장 자주 빠진다.** 백그라운드 명령이 실패했는데
그걸 못 보고 "이제 열어보세요"라고 안내하면 사용자만 헛걸음한다.

> 백그라운드로 뭔가 시작했으면 **살아 있는지 확인하기 전에는 안내하지 않는다.**

---

## 2. 사용자에게 묻는 것과 우리가 보는 것

| 우리가 본다 | 사용자에게 묻는다 |
|---|---|
| 버전, 로그, 프로세스, 설정 파일 | 폰·브라우저 **화면에 보이는 것** |
| 스토어·레지스트리 상태 | 물리적 상태 (전원, 연결) |
| 우리가 만든 파일 전부 | 우리가 접근할 수 없는 계정 화면 |

> **우리가 확인할 수 있는 것을 사용자에게 묻지 않는다.**
> 묻는 순간 "이 사람이 모르는구나"가 되고, 신뢰가 깎인다.

묻더라도 **설명을 요구하지 말고 화면을 받는다.** 비개발자는 증상을 언어화하지 못한다.

---

## 3. 검증 전에는 가설을 말하지 않는다

**"~일 거예요"를 사용자에게 말하지 마라.** 확인하고 나서 말한다.

| ❌ | ⭕ |
|---|---|
| "방화벽 문제일 가능성이 커요" (확인 안 함) | (조용히 확인) → "방화벽이 막고 있었어요. 열었습니다" |
| "버전이 낮은 것 같아요" | "확인해보니 폰은 54까지, 제가 만든 건 57이었어요" |

가설을 말하면 사용자는 그게 원인이라고 믿는다. **틀리면 두 번 실망한다** —
안 고쳐진 것과, 잘못 알려준 것.

**한 번에 하나의 가설만 검증한다.** 두 개를 동시에 바꾸면 뭐가 고쳤는지 모르고,
다음에 또 만나면 처음부터 다시 헤맨다.

---

## 4. 사용자가 할 수 없는 일을 시키지 않는다

행동을 요구하기 전에 **그 행동이 가능한지 우리가 먼저 확인한다.**

| 시키기 전에 확인할 것 |
|---|
| "업데이트하세요" → **업데이트가 실제로 존재하는가** |
| "이 버튼을 누르세요" → **그 버튼이 지금 버전에 있는가** |
| "다시 시도하세요" → **바뀐 게 있는가.** 같은 조건이면 같은 결과다 |

마지막이 특히 중요하다. **아무것도 안 바꾸고 "다시 해보세요"는 사용자를 소모시킨다.**

---

## 5. 세 번 실패하면 멈춘다

**"같은 오류 3회"가 아니라 "같은 목표에서 3회"로 센다.**
증상이 달라도 목표가 같으면 같은 실패다. (위 사례는 증상이 매번 달라서 카운트가 안 됐다)

세 번째 실패 뒤에는 **더 시도하지 말고** 셋 중 하나를 한다.

```
이 방법이 계속 안 되네요. 만든 건 하나도 안 없어졌어요.

 ① 다른 방법으로 해보기 (○○ 방식이 있어요)          ← 추천
 ② 지금 화면을 보여주시면 제가 정확히 확인할게요
 ③ 이건 나중에 하고 다음 걸 먼저 만들기
```

**③이 있어야 사용자가 갇히지 않는다.** 이 단계 하나 때문에 제품 전체가 멈추면 안 된다.

---

## 6. 원인을 찾으면 사용자 잘못이 아님을 분명히 한다

비개발자는 안 되면 **자기가 뭘 잘못했다고 생각하고 조용히 떠난다.**

```
원인을 찾았어요. 사용자가 뭘 잘못하신 게 아니에요.
제가 만든 게 폰보다 최신이라 못 읽고 있었어요. 제 쪽을 맞추겠습니다.
```

그리고 **왜 그렇게 됐는지 한 줄**을 남긴다. 다음에 같은 일이 나면 사용자가 먼저 알아챈다.

---

## 7. 자주 만나는 것 — 여기부터 본다

### 만든 것이 사용자 기기에서 안 열릴 때

1. **우리가 켠 서버가 살아 있는가**
2. **양쪽 버전이 맞는가** — 우리가 만든 것 vs 기기에 깔린 것
3. 기기가 우리에게 도달 가능한가 (같은 망 / 터널)
4. 로그에 기기가 남긴 정보가 있는가

**2번이 압도적으로 흔한 원인인데 가장 늦게 확인된다.**
"최신으로 만들었으니 문제없겠지"가 함정이다 — **기기에 깔리는 건 항상 뒤처진다.**

### Expo 앱이 폰에서 안 열릴 때

```bash
devoffice expo status
```

이 한 줄이 **서버 상태 · 우리 SDK · 폰이 받을 수 있는 SDK**를 한 번에 보여준다.
**다른 걸 시도하기 전에 이걸 먼저 실행한다.**

원인이 버전 불일치면 **폰이 아니라 우리 쪽을 맞춘다.**
App Store 심사 때문에 Expo Go 는 늘 뒤처지고, 그건 사용자가 어쩔 수 없는 일이다.

### 배포한 것이 안 열릴 때

1. 빌드가 실제로 성공했는가 (로그)
2. 환경 변수가 배포 쪽에도 들어갔는가 — **로컬에만 있는 게 흔한 원인**
3. 캐시 (사용자에게 새로고침 안내)
