# 기능 만들기 — ②계약부터 ⑦출시까지

구체화(①)는 `devoffice-spec` 이 끝냈다. **사용자가 승인한 명세가 이미 있다.**
여기서는 그걸 실제로 만든다.

```
② 계약·계획   CTO        3분     (미결 있으면 여기서 한 번에 질문)
③ 지시        CTO        1분
④ 구현        서버 ∥ 화면  20분    ← 사용자는 기다리기만
⑤ 통합        CTO + 게이트 5분
⑥ 검증        QA → 사용자           ★ 사용자 차례
⑦ 출시        프로듀서
```

**사용자가 손대는 건 ⑥ 하나다** (②에서 질문이 나오면 하나 더).

---

## 시작 전

```bash
devoffice feature show      # 진행 중인 기능과 단계
devoffice gate spec         # 명세가 규격에 맞는지
```

**`gate spec` 이 막으면 여기서 멈춘다.** 명세가 부실한 채로 만들면 전부 다시 한다.

그리고 사용자에게 예고한다.

```
⏳ 이제 만들게요. 25분쯤 걸려요.
   중간에 화면이 조용해도 정상이에요.
   (제가 하는 중이어도 언제든 끼어들어 말씀하셔도 돼요. 하던 건 안 없어져요.)
```

---

## ② 계약·계획 — CTO 를 부른다

`cto` 에이전트에게 맡긴다. 산출물은 셋이다.

| 산출물 | 무엇 |
|---|---|
| `packages/contracts/<ID>.ts` | 주고받는 것의 모양. **CTO 만 쓴다** |
| `plan.md` 의 작업표 | 담당·완료조건·관련 AC |
| `plan.md` 의 준비물 | 테스트 계정·시드·직링크 |

```bash
devoffice gate plan
```

**막히면 CTO 에게 돌려보낸다.** 게이트가 검사하는 것들이 전부
"없으면 하류가 성립하지 않는 것"이다 — 담당 없는 작업, 매핑 안 된 AC,
재사용 조사 누락, 준비물 공란.

### 미결 사항이 나오면 — 여기서 한 번에 묻는다

CTO 가 `plan.md` 의 **"확인 필요"** 에 모아둔다.
**그때그때 묻지 말고 여기서 한 번에** 묻는다. 3번 나눠 묻는 것보다 1번에 3개가 훨씬 낫다.

질문 예산은 여전히 **기능당 2개**다. 넘으면 나머지는 가정하고 통보한다.

## ③ 작업을 등록하고 지시서를 만든다

```bash
devoffice task add T1 --owner backend  --title "전략 목록 API" --ac AC-1
devoffice task add T2 --owner frontend --title "전략 목록 화면" --ac AC-1,AC-2
```

**8개를 넘으면 막힌다.** 막히면 우회하지 말고 기능을 쪼갠다.

지시서는 `handoff/NN-cto→<담당>.md`. **받는 사람은 아무것도 모른다는 전제로 쓴다.**

가장 중요한 두 칸:
- **먼저 읽을 파일** — 경로를 명시한다. "관련 문서 참고"는 금지
- **재사용할 것** — CTO 가 실제로 조사해서 채운다. 없으면 "없음 (조사함)"

---

## ④ 구현 — 계약이 잠긴 뒤에만 병렬

`backend` 와 `frontend` 를 **동시에** 부른다.

**이게 "한 번에 하나씩" 위반이 아닌 이유:** 기능 여러 개가 아니라
**기능 하나의 앞뒤면**이고, 계약이 경계를 잠그고 있다.
검증 단위는 여전히 기능 하나이고 사용자가 보는 것도 하나다.

웹·앱을 둘 다 만드는 제품이면 `frontend` 를 **두 번** 부른다 —
`apps/web` 에 한 번, `apps/mobile` 에 한 번. 둘 다 같은 계약을 쓰므로 자동으로 맞춰진다.

### 블로커가 올라오면

에이전트가 멈추고 블로커를 남긴다. **사용자 언어 객관식으로 바꿔 묻는다.**
첫 문장은 **"확인이 하나 필요해서 잠깐 멈췄어요"** — "문제가 생겼다"가 아니다.

---

## ⑤ 통합 — 게이트와 증거 대조

```bash
devoffice gate security     # L0 — 되돌릴 수 없는 것. 가장 먼저
devoffice gate l1           # 타입·빌드
devoffice gate l2           # 계약대로 응답하는지
```

**L0 이 막으면 다른 걸 보기 전에 고친다.** 권한·비밀키는 사고가 나면 되돌릴 수 없다.

그다음 CTO 에게 **증거 대조**를 맡긴다.

```
| AC   | 판정 | 근거                          |
| AC-1 | ✅  | server/routes/strategies.ts:14 |
| AC-4 | ❌  | 근거 없음 — 빈 상태 문구가 없음  |
```

**근거를 못 대면 미구현으로 간주한다.** ❌ 가 하나라도 있으면
사용자에게 가지 않는다. 고치고 다시 대조한다.

CTO 는 여기서 **"내 담당 아님" 신고도 전부 처리**한다.
구현 담당들이 서로 미룬 것이 여기서 잡힌다.

---

## ⑥ 검증 — 사용자 차례

`qa` 를 부른다. 산출물은 `verify.md` 와 **실제로 만들어진 준비물**이다.

QA 가 ❌ 를 보고하면 **사용자에게 보내지 않는다.** 고치고 다시 부른다.

통과하면 사용자에게 안내한다. **넷을 빠뜨리지 마라.**

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  📋 전략 고르기                  1/11
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

✅ 만들었어요. 폰 화면이 알아서 바뀌었을 거예요.

🔑 확인용 계정 (제가 미리 만들어뒀어요)
   test@test.com / test1234

 1. 전략 옆 스위치를 눌러보세요
    → 켜지고 위쪽 숫자가 "1개 켜짐" 으로 바뀌면 정상이에요

 2. 앱을 닫았다 열어보세요
    → 켠 상태가 남아 있으면 정상이에요

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
👉 잘 되면 "네", 이상하면 뭐가 이상한지 말씀해주세요
   설명이 어려우면 화면을 캡처해서 붙여넣어 주셔도 돼요

   ※ 화면이 그대로면 앱을 껐다 켜보세요
```

| 빠뜨리면 확인 자체가 불가능한 것 |
|---|
| **직링크** (홈 주소 말고 그 화면) |
| **테스트 계정** (로그인이 필요하면) |
| **"→ ~하면 정상이에요"** (없으면 판단 불가) |
| **새로고침 안내** |

사용자가 "네" 하면:

```bash
devoffice feature verify
```

**이걸 하기 전에는 다음 기능이 잠겨 있다.**

## ⑦ 출시 — 닫고 다음으로

```bash
git add -A && git commit -m "..."     # 기능 하나 = 커밋 하나
devoffice feature complete
devoffice state show
```

그리고 진척도와 **"이 속도면 언제 끝나는지"**를 보여준다.
끝이 안 보이면 사람은 그만둔다.

```
✅ 전략 고르기 완료

   ▓░░░░░░░░░░  11개 중 1개
   지금까지 만든 것: 전략 고르기

   다음: 종목에 전략 붙이기 (30분쯤)
   이 속도면 일주일쯤이면 다 만들어져요

👉 이어서 할까요, 오늘은 여기까지 할까요?
```

---

## 중간에 사용자가 끼어들면

| 말 | 대응 |
|---|---|
| "다음 것도 같이 해주세요" | 거절. 확인받고 나서 |
| "이건 나중에 할래요" | `devoffice feature cancel` — 만든 건 남는다 |
| "이거 말고 다른 걸 바꾸고 싶어요" | `devoffice-change` 스킬 |
| "지금 뭐 하는 중이에요?" | `devoffice feature show` 를 그대로 보여준다 |

---

## 하지 말 것

- **계약 없이 병렬 구현 시작하기** — 반드시 갈라진다
- `gate` 가 막는데 우회하기
- 증거 대조에서 ❌ 를 두고 사용자에게 보내기
- **준비물 없이 "확인해보세요"** 라고 하기
- 사용자 확인 없이 `feature complete`
- 지시서에 없는 것 만들기
- **"고쳐뒀어요"로 끝내기** — 고친 뒤에도 확인은 받는다
